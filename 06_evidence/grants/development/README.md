# Grant and Program Development

This directory contains **working grant-development and program-development materials** connected to Harmony for Hope, Inc., the New River Gorge Safety & Heritage Mesh Pilot, the Community Champion model, and related Mount Hope implementation planning.

These documents sit between early concepts and formal funding submissions.

They are intended to help Harmony for Hope develop:

* program architecture;
* cohort structures;
* implementation models;
* training approaches;
* budgets;
* schedules;
* field roles;
* stewardship models;
* evaluation methods;
* transferability plans;
* and grant-ready program descriptions.

The presence of a document in this directory does **not** mean that the program has been funded, submitted to a funder, approved, launched, or implemented.

---

## Development Status

The records in this directory should be understood within the broader grant-development lifecycle:

```text
funding idea
    ↓
grant concept
    ↓
program / application development
    ↓
submitted application
    ↓
funder review
    ↓
award / decline / revision
    ↓
accepted award and approved scope
    ↓
implementation
    ↓
evaluation
    ↓
closeout
```

This directory represents the **program / application development** stage.

A highly developed document may contain:

* a detailed budget;
* participant roles;
* compensation assumptions;
* a training schedule;
* an implementation timeline;
* evaluation criteria;
* field procedures;
* or proposed deliverables.

That level of detail does **not** change its status.

```text
detailed development plan
        ≠
submitted application

submitted application
        ≠
award

award
        ≠
every requested activity approved

approved scope
        ≠
implementation
```

Only the stage actually supported by the evidence should be claimed.

# Community Champion Model

The Community Champion concept represents a **human stewardship and community implementation layer**.

It is intended to help bridge the gap between:

```text
technical system
        ↓
community introduction
        ↓
human understanding
        ↓
local observation
        ↓
governed feedback
        ↓
evaluation
        ↓
responsible refinement
```

A Community Champion should not be treated merely as:

* a system administrator;
* a salesperson;
* an installer;
* an authority figure;
* or an unstructured volunteer.

Likewise:

```text
participation
    ≠
technical authority

attendance
    ≠
competence

observation
    ≠
verified fact

local knowledge
    ≠
automatic system truth
```

The program-development materials are intended to define those boundaries before the model is implemented at scale.

---

# Community Champion Cohort vs. Six-Month QA/Testing Cohort

This distinction is important.

The Community Champion development materials in this directory are **not the same program** as the current six-month application and community testing cohort included in the first-year pilot budget.

## Current first-year testing cohort

The current pilot budget includes a **$30,000 six-month testing cohort** composed of five specialists:

* one QA/Test Lead; and
* four application/browser testers.

That cohort is intended to support structured testing of areas such as:

* application behavior;
* browsers;
* devices;
* accessibility;
* usability;
* public-facing workflows;
* defects;
* reporting;
* and real-world system interaction.

---

## Community Champion development model

The Community Champion materials explore a broader human and community-stewardship function involving areas such as:

* local leadership;
* facilitation;
* resident support;
* community observation;
* field learning;
* documentation;
* stewardship;
* implementation support;
* and transferability.

The two models may eventually complement each other.

They should not be conflated.

```text
Community Champion cohort
        ≠
six-month QA/testing cohort
```

A budget or participant model contained in one should not automatically be attributed to the other.

# Relationship to Physical Infrastructure

# Development Record vs. Submitted Record

The repository should preserve both.

For example:

```text
development draft
        ↓
revised development plan
        ↓
application-specific adaptation
        ↓
submitted version
```

The submitted version should not replace or overwrite the development history.

Likewise, the development file should not later be relabeled as “submitted” merely because portions of it were used in an application.

# Budget and Schedule Discipline

Budgets, dates, cohort sizes, compensation structures, and timelines in this directory should be treated according to their documented status.

Unless supported by a submission, award, contract, or governing project document, they remain:

* working assumptions;
* scenario models;
* estimated costs;
* development targets;
* or proposed schedules.

A detailed budget is useful because it makes a program testable and fundable.

It is not evidence that money has been committed.

# Evidence and Provenance Standard

When these materials are used to support future applications or implementation, H4H should preserve the distinction among:

| Record                | What It Demonstrates                            |
| --------------------- | ----------------------------------------------- |
| Development framework | Program architecture has been explored          |
| Draft budget          | Costs have been modeled                         |
| Draft timeline        | Sequencing has been planned                     |
| Partner discussion    | A conversation occurred                         |
| Support letter        | Support was expressed                           |
| Submitted application | A request for funding was formally made         |
| Award notice          | A funder selected or awarded the application    |
| Accepted award        | H4H accepted the award conditions               |
| Approved scope        | Specific activities are authorized by the award |
| Implementation record | Work actually occurred                          |
| Evaluation record     | Outcomes were measured                          |

No lower stage should be represented as proof of a higher stage.

# Stewardship Principle

This directory exists so Harmony for Hope can develop ambitious programs **without erasing the difference between imagination, design, funding, authority, and implementation**.

The governing principle is:

```text
develop boldly
    ↓
label status accurately
    ↓
preserve provenance
    ↓
submit intentionally
    ↓
implement only when authorized
    ↓
evaluate what actually happens
```

Detailed development is valuable.

It becomes stronger — not weaker — when the repository is precise about what has and has not yet occurred.
