# Submitted Applications

## Read This First

This directory contains **submitted grant and funding applications** and the supporting records associated with each submission for the New River Gorge Safety & Heritage Mesh Pilot and related Harmony for Hope program development.

A submitted application is a **historical evidence record**.

Once an application has been filed with a funder, agency, partner, program, competition, or review body, the version that was submitted should not be silently rewritten to match later project development.

Corrections, revised requests, funder questions, award notices, declines, negotiations, accepted awards, approved scopes, and later correspondence should be preserved as separate dated records.

---

# Purpose

This directory preserves evidence of:

* what application was submitted;
* which funder, agency, program, or organization received it;
* when it was submitted;
* what deadline applied;
* what project title was used;
* what amount was requested;
* what narrative was submitted;
* what budget was submitted;
* what attachments accompanied the request;
* how submission was confirmed;
* who submitted it;
* what later correspondence occurred;
* what decision was issued;
* what scope was ultimately accepted, if any;
* and whether the funded activity later moved into implementation.

The purpose is to preserve the **actual funding history**, not merely the final version of the project as it exists today.

---

# Submitted-Application Status

A submitted application sits within the broader grant lifecycle:

```text
concept
    ↓
program / application development
    ↓
submitted application
    ↓
funder review
    ↓
revision / clarification if requested
    ↓
award / decline / withdrawal
    ↓
award acceptance if applicable
    ↓
approved scope / agreement
    ↓
implementation
    ↓
evaluation
    ↓
closeout
```

These stages should remain distinguishable.

In particular:

```text
submitted
    ≠
awarded

awarded
    ≠
accepted award

accepted award
    ≠
every requested activity approved

approved scope
    ≠
implementation

implementation
    ≠
successful outcome
```

Only the stage actually supported by the record should be claimed.


Current example:


This structure makes it easy to distinguish:

* submission year;
* submission month;

# Application Folder Structure

Each application should receive its own folder.

Recommended structure:

```text
application-name/
├── README.md
├── 01_Submitted_Application.pdf
├── 02_Submitted_Budget.pdf
├── 03_Submitted_Attachments/
├── 04_Submission_Confirmation.pdf
└── 05_Follow-Up_and_Decision/
```

Not every submission will contain every item.

The folder should preserve whatever evidence actually exists.

Additional records may include:

* portal screenshots;
* confirmation emails;
* letters of inquiry;
* supplemental questions;
* revised budgets;
* requested clarifications;
* interview materials;
* award letters;
* grant agreements;
* decline notices;
* or closeout correspondence.

# Required Application README

Each application folder should contain a short `README.md` describing the submission.

Recommended fields include:

* **Funder, agency, program, or receiving organization**
* **Submission date**
* **Deadline**
* **Amount requested**
* **Project title used**
* **Applicant organization**
* **Submitting person or authorized representative**
* **Submission method**
* **Confirmation or tracking information**
* **Current verified status**
* **Decision date, when known**
* **Amount awarded, if different from amount requested**
* **Accepted award date, if applicable**
* **Approved scope reference, if applicable**
* **Related project-development materials**
* **Related implementation materials, if the award later moves into implementation**

The README should summarize the record.

It should not replace the source documents.

# Recordkeeping Rule

The governing rule for this directory is:

> **Preserve what was actually submitted.**

A historical application may contain:

* an earlier budget;
* an earlier project description;
* a different implementation sequence;
* a technology later removed;
* a broader request than the eventual award;
* a narrower request than later project development;
* or language that no longer reflects the current project.

That is acceptable.

The submitted record should remain intact because it documents what the funder actually received.

---

# Do Not Retroactively Reconcile Submitted Applications

Current project documents may later change.

For example:

```text
submitted application
        ↓
project refinement
        ↓
current master budget
        ↓
current implementation plan
```

The original application should **not** be rewritten to make all four stages identical.

Instead, preserve both:

```text
historical submitted record
        +
current governing project record
```

That difference is useful evidence of project development.

# Status Definitions

Use the most specific verified status available.

| Status                               | Meaning                                                             |
| ------------------------------------ | ------------------------------------------------------------------- |
| **Submitted**                        | Application was delivered or filed                                  |
| **Submission confirmed**             | Receipt or portal confirmation exists                               |
| **Under review**                     | Funder has not issued a final decision                              |
| **Additional information requested** | Funder requested clarification or supporting material               |
| **Invited to revise**                | Funder requested or permitted a revised submission                  |
| **Resubmitted**                      | A revised application was formally filed                            |
| **Awarded**                          | Funder issued an award or selection notice                          |
| **Award pending acceptance**         | Award issued but formal acceptance or agreement is not yet complete |
| **Accepted award**                   | Applicant accepted the award or executed the required agreement     |
| **Approved scope established**       | Funded activities and conditions are documented                     |
| **Implementation underway**          | Work authorized by the accepted award has begun                     |
| **Completed / closed out**           | Funded work and required reporting have been completed              |
| **Declined**                         | Application was not selected                                        |
| **Withdrawn**                        | Applicant withdrew the request                                      |
| **Expired / not pursued**            | Opportunity did not advance to active funding                       |
| **Unknown**                          | Submission is documented but current outcome has not been verified  |

# Award Does Not Automatically Equal Requested Scope

A grant application may request several activities.

An award may:

* fund the full request;
* fund only part of it;
* reduce the amount;
* remove activities;
* add conditions;
* require a revised budget;
* require a revised timeline;
* restrict costs;
* or require further approval before implementation.

Therefore:

```text
requested scope
        ≠
approved scope
```

When an award occurs, preserve:

1. the submitted request;
2. the award notice;
3. the accepted agreement;
4. the final approved budget;
5. the final approved scope;
6. and later implementation evidence.

# Amount Requested vs. Amount Awarded

These should be recorded separately.

Example:

| Financial status      |                        Amount |
| --------------------- | ----------------------------: |
| Requested             |                       $XX,XXX |
| Awarded               |                       $XX,XXX |
| Accepted / contracted |                       $XX,XXX |
| Expended              | Document later if implemented |

A requested amount should never be represented as grant revenue merely because an application exists.

# Application vs. Current Pilot Budget

Historical applications may contain budgets that differ from the current project budget.

That does not make either record incorrect.

They serve different purposes.

The submitted application records:

> **What was requested from that particular funder at that particular time.**

The current master pilot budget records:

> **The current governing funding model for the first-year Mount Hope implementation.**

Current governing budget:

[`../../../../03_project/pilot_budget/Master_First_Year_Pilot_Budget.md`](../../../../03_project/pilot_budget/Master_First_Year_Pilot_Budget.md)

Current first-year funding target:

**$53,244**

comprising:

* **$23,244** — Mount Hope/FCCAC public anchor and program costs;
* **$30,000** — six-month application and community testing cohort.

A separate preliminary **$7,592 Thurmond physical-build planning estimate** remains outside the current Mount Hope first-year request.

Historical submitted budgets should remain historical even when they differ.

# Community Champion Boundary

Submitted applications may refer to Community Champion activities.

Those references should be interpreted according to the application that was actually submitted.

They should not automatically be equated with the current six-month QA/testing cohort.

The current QA/testing cohort consists of:

* one QA/Test Lead; and
* four application/browser testers.

Community Champion development may instead involve:

* community stewardship;
* facilitation;
* resident support;
* field learning;
* observation;
* leadership;
* documentation;
* and transferability.

Therefore:

```text
Community Champion activity
        ≠
QA/testing cohort
```

unless a specific submitted or approved funding record explicitly combines them.

# Mount Hope and Thurmond Status

Current repository framing distinguishes:

**Mount Hope**
= initial/current implementation and funding path.

**Thurmond**
= future federal-phase implementation opportunity, with documented support, contingent on separate federal funding, National Park Service review/compliance, site-specific approval, technical review, and final agreements.

Historical applications should not be rewritten merely because this status language was refined later.

However, current README summaries and current status notes should use the repository's current terminology when explaining how an older application relates to the project today.

# Revised Applications

If a funder requests a revised application, preserve both versions.

Example:

```text
01_Submitted_Application_Original.pdf
02_Submitted_Budget_Original.pdf
05_Follow-Up_and_Decision/
    ├── Request_for_Revision.pdf
    ├── Revised_Application.pdf
    ├── Revised_Budget.pdf
    └── Resubmission_Confirmation.pdf
```

Do not replace the original application with the revision.

Both are part of the evidence chain.

# Declined or Unfunded Applications

Declined applications remain useful project evidence.

They may document:

* funder fit;
* program development;
* unsuccessful strategy;
* prior project framing;
* budgets;
* reviewer feedback;
* and later refinement.

A decline does not erase the development value of the application.

The status should simply remain accurate.

# Public Release and Privacy

Before placing application materials in a public repository, review them for:

* personally identifiable information;
* personal addresses;
* signatures;
* phone numbers where inappropriate for public release;
* private email addresses;
* financial-account information;
* banking information;
* tax documents;
* portal credentials;
* passwords;
* private partner information;
* protected organizational records;
* proprietary material;
* and funder-specific confidentiality requirements.

Do not publish sensitive information merely because it appeared in a submitted application.

Where necessary:

* redact;
* withhold;
* summarize;
* or maintain the authoritative copy internally.

---

# Record Integrity

Whenever practical, preserve:

* original PDF;
* original filename;
* submission confirmation;
* file date;
* submission date;
* correspondence;
* and decision records.

If a public copy has been redacted, label it clearly as a redacted public copy.

Do not represent a recreated document as the exact submitted original unless that can be verified.

# Relationship to Implementation Evidence

If an application is awarded and accepted, implementation evidence should not remain buried only inside the submitted-application archive.

The application folder should link to the relevant implementation or evidence record.

Implementation documentation may include:

* approved budget;
* approved scope;
* implementation plan;
* asset record;
* invoices;
* procurement records;
* field evidence;
* commissioning evidence;
* evaluation;
* and closeout reporting.

The application proves funding history.

The implementation record proves what actually happened.

---

# Stewardship Principle

Submitted applications are not marketing drafts once they have been filed.

They are **historical evidence**.

The governing rule is:

```text
submit
    ↓
preserve
    ↓
record what changed
    ↓
record the decision
    ↓
separate award from approved scope
    ↓
separate approved scope from implementation
    ↓
preserve outcome evidence
```

This allows reviewers, funders, partners, and future H4H leadership to reconstruct the project's funding history accurately.
